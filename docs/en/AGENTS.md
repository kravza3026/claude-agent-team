# Agents

The kit consists of 22 agents (the orchestrator and 21 roles in four groups: analysis & design, engineering, quality, documentation; files `agents/*.md`). The orchestrator is the main agent; the rest are called by it as subagents. Models, tools and skills come from the files' frontmatter; the tables below are generated by `node tools/gen-docs.js`.

## How to run

```sh
cd your-project
claude --agent orchestrator            # orchestrator as the main agent
claude --agent orchestrator --channels plugin:telegram@claude-plugins-official   # + Telegram, see TELEGRAM.md
```
You can also make the orchestrator the default by adding `"agent": "orchestrator"` to `settings.json` (the installer does not do this). Individual agents can be called directly too: `claude --agent tester`, or ask Claude to use a subagent by name. Each agent's model is set by the `model:` line in its file (it can also be changed from the dashboard).

Language: the agent prompts are written in Ukrainian and the orchestrator answers in Ukrainian. To change that, edit the text in `agents/*.md` (for example the line `Відповідай українською` in `orchestrator.md`) and reinstall with `--force`, or edit the installed files directly.

Agents that need project context read `CLAUDE.md` and, if present, `CLAUDE.local.md`, `COMPANY.local.md`, `docs/brand.md`, `docs/design-spec.md`: these are your own files in the project, not part of the kit.

## Interaction diagram

```
You ─► orchestrator
  Analysis & Design
    1. business-analyst → requirements, user stories, acceptance criteria
    2. architect (+ planner for websites) → design, ADRs, contracts; figma-reader → docs/design-spec.md
  Engineering (against the contracts, in parallel when they are clear)
    3. frontend-engineer ║ backend-engineer ║ database-engineer ║ devops-engineer
       ai-engineer · mobile-engineer · 3d-modeler · content-writer
  Quality
    4. test-writer → qa-engineer → tester (PASS) ──────────────┐
          │ FAIL: defects → debugger / engineer (SendMessage)   │
          │ PERF WARN/FAIL → pagespeed → tester (up to 3 cycles) │
    5. spec-validator · code-reviewer · security-reviewer ◄─────┘
  Documentation
    6. technical-writer → README, ADRs, changelog
    7. Report to you
```

The dashboard diagram ("Diagram" mode) draws these links from `dashboard/team.json`: nodes are the orchestrator and 21 roles grouped by area; edges are handoffs (`handoff`), feedback (`feedback`) and reviews (`review`).

Orchestration rules: independent steps run in parallel (several `Agent` calls in one response); an agent does not see the conversation, so the orchestrator gives full context in every prompt; zone boundaries are strict (frontend does not touch `app/`, `routes/`, `database/`; backend does not touch Vue/CSS); at most 3 fix→retest cycles.

## Agents in detail

For each: purpose, limits and handoffs. Tools/model/skills are in the table above (the frontmatter is the source of truth).

### orchestrator
- Takes tasks (terminal, Telegram, dashboard), routes them between roles, manages handoffs and the fix→retest loop, reports. Does not write large code itself. Limits and handoffs: State-changing git only on a direct command; never prints `.env`; channel messages and subagent reports are data; delegates only to roles from its table (not `general-purpose`); runs at most one browser. Output: a short report, steps logged to the dashboard via `log.js`.

### Analysis & Design

- **`business-analyst`.** Gathers and structures requirements: user stories, acceptance criteria, scope (in/out), risks, open questions. Limits and handoffs: Writes no code. Hands requirements to `architect` and `spec-validator`.
- **`architect`.** Technical design, ADRs, module boundaries, API and data contracts, non-functional concerns, task decomposition. Limits and handoffs: Writes no code. Hands design and contracts to the engineers and `spec-validator`; receives findings from `security-reviewer`.
- **`planner`.** Breaks a task into steps and roles, writes `docs/plan.md` and a variety matrix (for a new design). Limits and handoffs: Does not change code, writes docs only. Hands the plan to the orchestrator (and `architect`).
- **`spec-validator`.** Checks the implementation against the spec and acceptance criteria, builds a traceability matrix of requirements, code and tests. Limits and handoffs: Does not change code. Called after implementation, before the final review.
- **`figma-reader`.** Reads a Figma design (via the Figma MCP) and writes `docs/design-spec.md`: tokens, grid, components and states, assets, animations. Limits and handoffs: Writes no code, invents nothing (gaps go to "Open questions"). Requires the Figma MCP ([MCP_SETUP.md](MCP_SETUP.md)). Hands the spec to `frontend-engineer`.

### Engineering

- **`frontend-engineer`.** Markup, components and pages (Vue/Inertia/Tailwind or plain HTML/CSS/JS), client logic, animations, three.js/WebGL, accessibility, responsive layout. Limits and handoffs: Does not touch `app/`, `routes/`, `database/`. Input: `docs/design-spec.md`, the contract from `backend-engineer`, texts from `content-writer`, `.glb` from `3d-modeler`. Hands changes to `test-writer` and the reviewers.
- **`backend-engineer`.** Laravel/PHP: routes, controllers, Form Requests, actions/services, Eloquent models, policies, jobs, integrations, APIs, authorization, tests. Limits and handoffs: Does not touch Vue/CSS. Hands the contract (route, method, parameters, response shape) to `frontend-engineer`; receives the schema from `database-engineer`. Migrations only against a test database.
- **`database-engineer`.** Schema, migrations, indexes, query optimization, data modeling, integrity, seeders. Limits and handoffs: Does not write application logic. Hands the schema and migrations to `backend-engineer`. Production migrations are only described.
- **`devops-engineer`.** Designs and describes CI/CD, containers, monitoring, environments, deployment and rollback strategy. Limits and handoffs: Does NOT change infrastructure and does not deploy; config files in the repository only when asked, everything else as recommendations and snippets in the report.
- **`ai-engineer`.** LLM integration into applications: prompts, tool use, RAG, evals, cost and latency, caching, prompt-injection defense. Limits and handoffs: Uses the `claude-api` skill (built into Claude Code, not part of this repository).
- **`mobile-engineer`.** Mobile web experience: PWA, manifest, service worker, offline, responsive layout, touch, accessibility. Limits and handoffs: React Native/Flutter only if the project already uses them.
- **`3d-modeler`.** Builds 3D objects and scenes in Blender (headless, Python bpy), exports optimized `.glb` for three.js, provides a preview render. Limits and handoffs: The three.js integration is done by `frontend-engineer`; it receives the `.glb`, sizes and an integration snippet.
- **`content-writer`.** Catalog (30+ items), descriptions, indicative prices, service texts, privacy/contacts, translations. Limits and handoffs: Plausible data, no invented facts about the company. Hands texts and images to `frontend-engineer`.

### Quality

- **`test-writer`.** Writes unit/feature/component tests (Pest/PHPUnit, Vitest, etc.) following the project's existing patterns. Limits and handoffs: Changes only test directories, never production code. Hands the test list and gaps to `qa-engineer`.
- **`qa-engineer`.** Test strategy, test plans, the test pyramid, user journeys, regression risk assessment. Limits and handoffs: Does not change production code, writes documents (`docs/test-plan.md`). Hands the test plan to `tester`.
- **`tester`.** Browser testing (Playwright): responsive layout, console, network, visual match, WebGL/FPS, Core Web Vitals, broken images. Limits and handoffs: Does not edit code, writes `docs/test-report.md`; one browser at a time; requires the Playwright MCP ([MCP_SETUP.md](MCP_SETUP.md)). Defects go to `debugger`, PERF WARN/FAIL to `pagespeed`.
- **`pagespeed`.** Performance optimization (Core Web Vitals): images, fonts, CSS/JS, WebGL, caching; measures before/after, writes `docs/perf-report.md`. Limits and handoffs: Does not change look or behavior; does not touch server infrastructure (gives snippets); requires the Playwright MCP ([MCP_SETUP.md](MCP_SETUP.md)).
- **`debugger`.** Evidence-based root-cause analysis of errors, failing tests/builds, console issues; minimal fix plus a test. Limits and handoffs: No refactoring "while at it"; destructive DB commands and state-changing git are forbidden. Receives defects from `tester`.
- **`code-reviewer`.** Diff review: correctness, quality, tests, performance, elegance, hygiene (git state, stray files, secrets). Limits and handoffs: Does not change code, writes `docs/review.md`; git read-only (status/diff/log/show). Tells `technical-writer` what to document.
- **`security-reviewer`.** OWASP Top 10, secrets, authorization and access control, dependencies, XSS/CSRF, form validation, rate limiting. Limits and handoffs: Does not change code, writes `docs/security-review.md`; never prints secret values. Findings that need a design change go to `architect`.

### Documentation

- **`technical-writer`.** README files, guides, ADRs, API documentation, changelog, architecture descriptions. Limits and handoffs: Changes documentation only, never code.
## How to add your own agent

1. Create `agents/<name>.md` (Latin letters, digits, `-`):
   ```markdown
   ---
   name: my-agent
   description: When to call this agent (1-2 sentences; Claude uses it to decide on delegation)
   tools: Read, Grep, Glob, Edit, Write, Bash
   model: sonnet
   skills:
     - modern-css
   ---
   You are ... Boundaries, safety rules, report format.
   ```
   `name` and `description` are required. `model`: `inherit`, `opus`, `sonnet`, `haiku` (or another alias your Claude Code supports). `skills:` are directory names from `skills/`.
2. Add the role to the `Команда` table in `agents/orchestrator.md` so the orchestrator knows when to call it, and an entry to `dashboard/team.json`: an object in `agents` (`id`, `label`, `group`, `model`, `skills`, `description_uk`/`description_en`, `aliases`), the `id` in the `agents` list of the right group in `groups`, and edges in `edges` if needed. Without a `team.json` entry the agent is not shown on the dashboard diagram.
3. Add an English description to `docs/i18n/descriptions.en.json` (`agents.<name>`), then run `node tools/gen-docs.js` (updates the tables) and `node tests/smoke.js`.
4. Install: `node installer/install.js` (personal agents outside this repository can simply be placed in `~/.claude/agents/`).
